# Report Generation Document

## 1. Overview

This document defines the report-generation feature for the Health Assessment System. The goal is to convert recorded health assessment data into readable summaries for health workers, barangay officials, and administrators.

The project already stores assessment data in the backend and exposes dashboard summaries in the frontend. Report generation should build on these existing structures instead of creating a separate, disconnected reporting layer.

## 2. Objectives

The reporting system should:

- summarize daily, weekly, and monthly health assessment activity
- identify urgent cases, follow-up cases, and barangay trends
- support resident history views and admin-level analytics
- provide data in a format suitable for print, PDF, CSV, or screen export
- improve decision-making for RHU and barangay monitoring

## 3. Report Use Cases

### 3.1 Resident Report
A resident may want to see a personal report such as:

- assessment date
- detected symptoms
- risk level
- recommendation
- explanation of the result
- advisory guidance

This aligns with the current history and result pages in the app.

### 3.2 Barangay Summary Report
A health worker or MHO may need a report that includes:

- total assessments by barangay
- number of RED and YELLOW cases
- most common symptoms reported
- weekly trend of submissions
- urgent cases requiring follow-up

### 3.3 Administrative Overview Report
Administrators may need a broader report for planning and coordination:

- total residents assisted
- community-level risk trends
- hotspot barangays
- trend of symptom clusters
- generated at a selected date range

## 4. Existing Data Model

The current system already has the main data needed for report generation.

### 4.1 Assessment record
From the backend data model, an assessment contains:

- id
- user_id
- input_text
- method
- detected_symptoms
- risk_level
- reason
- recommendation
- created_at

This is sufficient for single-case reports and trend summaries.

### 4.2 Dashboard metrics already available
The API already prepares summary data including:

- total assessments
- cases today
- cases in the last 7 days
- urgent alerts
- follow-up cases
- barangay statistics
- top symptoms
- method breakdown
- weekly trend

These fields are ideal for report generation and should be reused wherever possible.

## 5. Recommended Report Types

### 5.1 Daily Summary Report
Purpose:
- monitor daily assessment volume
- check urgency levels in a 24-hour period

Suggested sections:
- total assessments completed
- RED cases
- YELLOW cases
- GREEN cases
- top symptoms reported
- notable barangays

### 5.2 Weekly Health Report
Purpose:
- provide a community-level overview for health staff
- detect recurring symptom clusters

Suggested sections:
- weekly trend by day
- total assessments
- urgent alerts
- follow-up cases
- barangay comparison
- symptom frequency ranking

### 5.3 Monthly Community Risk Report
Purpose:
- support RHU planning and intervention decisions
- review patterns over time

Suggested sections:
- monthly totals
- barangay ranking
- top symptoms
- RED case trends
- summary of recommendations and referrals

### 5.4 Individual Assessment Report
Purpose:
- generate a patient-friendly result summary
- provide a downloadable record

Suggested sections:
- resident name or identifier
- date and time of assessment
- symptoms captured
- diagnosis explanation
- recommendation and guidance
- disclaimer

## 6. Report Structure

Every generated report should follow a consistent structure.

### Header
- report title
- report type
- generated date and time
- generated by
- barangay or scope

### Summary
- total count
- urgent count
- follow-up count
- key highlights

### Main Data Section
- table or chart-based results
- filtered by date range and barangay

### Insights
- top symptoms
- highest-risk barangays
- alert notices
- recommended action

### Footer
- data source
- generation timestamp
- confidentiality note

## 7. Filtering and Scope

Reports should support filtering by:

- date range
- barangay
- risk level
- symptom category
- user role or resident status
- assessment method (text vs symptom chips)

A good default is:

- last 7 days for operational reporting
- last 30 days for planning reports
- all-time for admin summary and archive use

## 8. Business Rules for Report Generation

1. RED cases must always appear at the top of urgent summaries.
2. YELLOW cases must be counted as follow-up or review tasks.
3. Empty results or missing barangay values should be labeled as "Unassigned / walk-in".
4. A report should never show raw private data without purpose or consent.
5. Report generation should include only records within the selected date range.
6. Records should be sorted by created_at in descending order for recent reporting.

## 9. Suggested API Design

The backend should expose dedicated endpoints such as:

- GET /reports/summary
- GET /reports/weekly
- GET /reports/barangay
- GET /reports/resident/{id}
- GET /reports/export/csv
- GET /reports/export/pdf

### Example response for summary report

```json
{
  "report_type": "weekly_summary",
  "generated_at": "2026-08-31T10:00:00Z",
  "filters": {
```

## 10. Frontend Integration

The report page should live in the admin or dashboard flow and probably reuse existing data from the summary endpoints.

Recommended UI sections:

- date range selector
- barangay filter
- risk filter
- download as CSV or PDF button
- summary cards
- chart blocks
- recent assessment table

## 11. Export Formats

### CSV
Best for:
- spreadsheet analysis
- sharing with local agencies
- offline reporting

### PDF
Best for:
- formal reports
- printing
- official summaries

### HTML view
Best for:
- screen display
- internal review before export

## 12. Implementation Plan

### Phase 1: Core reporting endpoints
- create summary endpoint from existing assessment data
- expose active filters and trend data
- return structured JSON for frontend consumption

### Phase 2: UI report page
- build admin dashboard report view
- show summary cards and charts
- allow filter selection by date and barangay

### Phase 3: Export support
- generate CSV for raw records
- generate PDF for official summaries

### Phase 4: Automation
- schedule daily or weekly report generation
- auto-email selected report summaries to health officers

## 14. Success Criteria

The report generation feature is successful when:

- health workers can create summary reports in minutes
- data is accurate and tied to real assessment records
- trends are easy to understand
- urgent cases stand out clearly
- reports are exportable and printable

## 15. Recommendation

The best approach for this project is to build report generation on top of the already existing dashboard summary logic and stored assessment data. This reduces duplication, keeps the system consistent, and makes future enhancements easier.

In short:
- reuse the assessment schema
- reuse dashboard metrics
- extend with date-range and export filters
- present reports in a structured admin-facing UI

## 16. Final Note

This project is already close to having a strong reporting foundation because the backend tracks assessment data and the dashboard summary already computes community-oriented metrics. By formalizing the report endpoints and report templates, the system can evolve into a reliable decision-support tool for health monitoring and community response.
